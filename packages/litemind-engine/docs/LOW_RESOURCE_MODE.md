# Режим Low Resource — защита слабых компьютеров

Профиль **Low Resource** включён по умолчанию. Он рассчитан на контрольное оборудование:
Windows 10/11, 16 ГБ RAM, встроенная графика (~3 ГБ выделяемой видеопамяти),
без дискретной видеокарты.

## Настройки по умолчанию

| Параметр | Значение | Что даёт |
|---|---|---|
| `maxConcurrentRequests` | **1** | ровно один активный запрос — генерация не дерётся с системой |
| `queueLimit` | 16 | избыток запросов отклоняется `429 QUEUE_FULL` вместо наматывания очереди |
| `contextTokens` | 2048 | небольшой контекст, если модель его поддерживает |
| `maxOutputTokens` | 512 | ограниченная длина ответа |
| `cpuThreads` | 2 | меньше потоков CPU → система остаётся отзывчивой (`num_thread` в Ollama) |
| `requestTimeoutMs` | 120 000 | общий предел времени запроса |
| `streamIdleTimeoutMs` | 60 000 | «зависший» стрим обрывается, слот освобождается |
| `idleUnloadSeconds` | 300 | через 5 минут простоя модель выгружается из памяти (`keep_alive: 0`) |
| `memoryReserveMb` | 2048 | резерв под Windows: в него модели не «заглядывают» |
| `maxRamUsageFraction` | 0.75 | отказ, если после загрузки модели RAM превысит 75% от TOTAL |
| `autoLoadAtStartup` | false | тяжёлые модели **не** загружаются при старте |
| `allowAutoDownload` | false | никаких автоматических скачиваний моделей и Ollama |

В переключении режима «Экономия ресурсов» в панели (или `POST /api/profile`) используется
профиль `low`; выключенный режим — профиль `balanced` (2 параллельных запроса, контекст 4096),
он по-прежнему остаётся консервативным.

## Проверка памяти перед запуском

Расчёт (см. `src/resource/gate.js`):

```
прогноз = размер модели (из списка Ollama)
        + KV-кэш: contextTokens × 64 КБ/токен      (настраивается: kvOverheadKbPerToken)
        + 256 МБ  накладных расходов backend'а

бюджет_доступно = available RAM − 2048 МБ (резерв Windows)
```

Решение принимается по трём условиям:

1. **Блокировка**, если `прогноз > доступно − резерв`. Ответ: `503 MEMORY_BUDGET`
   с текстом «Forecast N MB exceeds safe budget …», backend к этому моменту не тронут.
2. **Блокировка**, если `used RAM + прогноз > 75% TOTAL RAM` — защита от ситуации,
   когда «вроде хватает», но Windows начинает подвисать из-за подкачки.
3. **Предупреждение** (запуск разрешён), если прогноз занимает больше 80% бюджета —
   записывается в журнал и видно в панели.

Важно: оценка опирается на **доступную** память в момент запроса, а не на общий объём RAM,
и учитывает уже используемую память. Если размер модели определить не удалось, по умолчанию
запуск разрешается с предупреждением (политика `blockOnUnknownEstimate: true` запрещает такой
запуск полностью).

## Что LiteMind делает и чего не делает

Делает:

- один активный запрос, ограничение потоков, лимит контекста и ответа;
- немедленную выгрузку модели по таймеру простоя и по кнопке «Выгрузить модель»;
- ручную остановку генерации в один клик (корректную, через отмену HTTP-запроса);
- диагностику нехватки памяти и тайм-аутов с понятными сообщениями;
- освобождение всех слотов при любом исходе запроса (успешном, отменённом, по тайм-ауту,
  при сбое backend'а) — проверяется автотестами.

Не делает (намеренно):

- не завершает сторонние процессы Windows;
- не запускает модели автоматически при старте системы и не добавляет себя в автозагрузку;
- не скачивает модели и Ollama;
- не обещает полного отсутствия зависаний: слабая машина с моделью в памяти остаётся
  нагруженной, поэтому LiteMind скорее **предотвращает** перегрузку и показывает реальные
  цифры, чем «гарантирует» плавность. Фактические измерения — в [BENCHMARKS.md](BENCHMARKS.md).

## Ручное управление

- «Остановить» в панели → `POST /api/stop` → отмена активного и очередных запросов.
- `POST /api/cancel {"request_id": "req_..."}` → отмена конкретного запроса.
- «Выгрузить модель» → `POST /api/unload {"model": "имя"}` → `keep_alive: 0` в Ollama.
