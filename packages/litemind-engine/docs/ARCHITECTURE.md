# Архитектура LiteMind Engine

## Общий принцип

LiteMind — **управляющий** движок, а не вычислительный. Нейросети с нуля не реализуются:
первый релиз подключает существующий локальный backend (Ollama) через её HTTP API, а всю
политику защиты машины держит на своей стороне. Граница между ними — интерфейс
`src/backends/base.js`, поэтому второй backend (например, llama.cpp server) подключается
без изменения Core, API и панели.

## Компоненты (по ТЗ §2)

| № | Компонент | Файл | Ответственность |
|---|---|---|---|
| 1 | LiteMind Core | `src/core/engine.js` | жизненный цикл запроса, конфигурация, состояние, очередь |
| 2 | Resource Manager | `src/resource/metrics.js`, `src/resource/gate.js` | метрики RAM/CPU/VRAM, допуск к запуску по памяти |
| 3 | Model Manager | `engine.listModels()/unload()` + адаптер | обнаружение, выбор, запуск (ленивый), выгрузка моделей |
| 4 | Inference Backend | `src/backends/*` | адаптер выполнения; контракт + реестр |
| 5 | API Server | `src/api/server.js` | локальный OpenAI-совместимый API |
| 6 | Desktop UI | `src/ui/public/*` | лёгкая панель (статика, без сборки) |
| 7 | Diagnostics | `src/diagnostics/log.js` | журнал + метрики производительности |

## Поток запроса

1. Клиент (панель или OpenCode) → `POST /v1/chat/completions`.
2. API-сервер проверяет доступ (loopback/токен), парсит тело (лимит 1 МиБ), определяет режим
   (обычный или потоковый SSE).
3. Core создаёт запись запроса (`req_xxxxxxxx`, состояния: new → queued → running →
   done/cancelled/timeout/error) и берёт слот очереди. В профиле Low Resource слот один,
   остальные ждут; при переполнении очереди — `429 QUEUE_FULL`.
4. Перед запуском — **проверка памяти**: размер модели из списка backend'а + KV-кэш
   (`contextTokens × 64 КБ/токен` по умолчанию) + 256 МБ накладных расходов сверяются
   с `доступно − резерв Windows` и с потолком `75% от TOTAL RAM`.
   Не помещается → `503 MEMORY_BUDGET`, backend **не трогается**.
5. Адаптер Ollama выполняет `POST /api/chat` с `stream: true` и опциями
   `num_ctx`, `num_predict`, `num_thread`; токены идут в API как SSE-чанки.
6. Завершение/отмена/тайм-аут → освобождение слота, запись метрик (TTFT, длительность,
   токены/сек) и постановка таймера автовыгрузки.

## Отмена и тайм-ауты

- **Отмена клиента**: обрыв соединения → `AbortSignal` → закрытие сокета к Ollama,
  что останавливает генерацию на стороне backend'а (проверено тестом).
- **`POST /api/cancel {request_id}`** и кнопка «Остановить» (`POST /api/stop`) работают
  для активного и находящегося в очереди запросов.
- **Тайм-ауты**: общий (`requestTimeoutMs`, по умолчанию 120 с) и тайм-аут простоя стрима
  (`streamIdleTimeoutMs`, 60 с) — оба приводят к `504 TIMEOUT` и гарантированно
  освобождают слот (проверено тестом).
- Сторонние процессы Windows **не завершаются никогда**; принудительных kill нет вовсе —
  только корректная отмена через HTTP.

## Почему для v0.1 выбран Ollama, а не прямой llama.cpp

| Критерий | Ollama | Прямой llama.cpp |
|---|---|---|
| Контракт интеграции | стабильный HTTP: `/api/version`, `/api/tags`, `/api/chat` (стрим), `/api/ps`, `keep_alive: 0` для выгрузки | свой протокол/сервер, больше кода у нас |
| Установка на Windows | готовый установщик, служба | сборка или загрузка бинарей вручную |
| Управление памятью | выгрузка `keep_alive: 0`, ленивая загрузка | нужно своё управление процессом |
| Параллелизм | жёсткий лимит задаём мы (`maxConcurrentRequests=1`) | пришлось бы строить свою очередь |
| Наш контроль ресурсов | весь — на стороне LiteMind (очередь, бюджет, тайм-ауты) | больше рычагов, но и больше кода |

Вывод: Ollama даёт надёжный и простой контракт, а весь необходимый контроль ресурсов
реализуем на нашей стороне интерфейса. Поэтому Ollama выбрана как первый backend;
контракт `base.js` оставляет прямую интеграцию llama.cpp возможной без переделки Core.

## Почему Node.js, без тяжёлого UI

- Один процесс, **ноль production-зависимостей** (`npm install` не нужен).
- Панель — три статических файла; фоновых демонов, Electron и автообновлений нет.
- `node:test` — встроенный тестировщик, сборка воспроизводима: `npm test`.
- На Windows метрики берутся одним вызовом PowerShell/CIM, без сторонних библиотек.

## Точки расширения

- **Новый backend**: `registerBackend('имя', factory)` в `src/backends/registry.js`
  + реализация пяти методов контракта (`detect`, `listModels`, `capabilities`,
  `generate`, `unload`).
- **Новый профиль**: запись в `DEFAULT_PROFILES` (`src/config.js`).
- **Новый эндпоинт API**: функция `route()` в `src/api/server.js`.
